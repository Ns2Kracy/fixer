# Scrape Runs Design

**Date:** 2026-09-09
**Status:** Approved

## Context

Fixer currently exposes its persisted job state machine directly to users. A manual scrape creates a job, waits for candidate review, builds a plan, waits for execution approval, and finally writes files. The Web UI mirrors these internal stages through `/jobs`, review pages, plan pages, confidence labels, and explicit execution controls.

The intended product model is simpler: a user starts a scrape once, leaves the page, and later audits the result. Fixer should automatically choose the deterministic first match or fetch an explicitly supplied provider ID, write metadata, organize files, and preserve an immutable record of what happened. Incorrect results must be correctable without erasing history.

This is a domain rewrite rather than a frontend facade. The `Job` model, API, persistence, review state, confidence gates, and plan-confirmation workflow will be removed.

## Goals

- Make one click authorize and enqueue a complete scrape-and-organize run.
- Replace the user and server `Job` domain with `ScrapeRun`.
- Make completed and failed runs durable, immutable, and auditable without contacting providers again.
- Select the deterministic first provider result without confidence thresholds or ambiguity gates.
- Let users bypass search with an exact provider target, initially TMDB movie and television IDs.
- Let users correct a result by searching again or supplying another exact provider ID.
- Preserve prior attempts and safely replace only outputs generated by the previous run.
- Keep folder ingestion and restart recovery working.
- Use a maintained in-memory queue primitive rather than implementing a queue.

## Non-goals

- Distributed workers or a separately deployed broker.
- Parallel filesystem writers.
- Automatic overwrite of unrelated or manually modified files.
- Deleting all matching and identity logic. Exact cross-provider identity grouping remains useful, but numeric confidence does not.
- Preserving the old public `/jobs` API.

## Product Model

A `ScrapeRun` is one immutable attempt to turn one discovered source into organized media output.

A run has four public states:

- `queued`
- `running`
- `succeeded`
- `failed`

Scanning, searching, resolving, planning, and writing are transient progress phases. They are not durable domain states and do not require user actions.

A run is one of:

- `initial`: created from the scrape page or a folder rule.
- `retry`: repeats a failed run with the same selection.
- `correction`: supersedes a prior result with a newly selected provider target.

Corrections never mutate an earlier run. They create a linked run through `previous_run_id`. A successful newer run is the current result, while every prior result remains available for audit.

## Core Changes

The behavior belongs in `fixer-core` and `fixer-sdk`; the server must not emulate a scrape by chaining old review endpoints.

### Deterministic matching without confidence

`fixer-core` will remove the public `Confidence` value, floating-point scoring, confidence thresholds, and ambiguous-top-score behavior from:

- `crates/fixer-core/src/confidence.rs`
- `crates/fixer-core/src/matching/mod.rs`
- `crates/fixer-core/src/matching/score.rs`
- matching errors and exports in `crates/fixer-core/src/error.rs` and `crates/fixer-core/src/lib.rs`

Candidate ordering remains deterministic but categorical:

1. Exact external-ID identity.
2. Exact normalized title and year.
3. Exact normalized title.
4. Provider registration order.
5. Provider-native result order.

Exact identity grouping used by television and anime remains. Search results no longer carry a numeric confidence, no tie is considered a blocking ambiguity, and automatic selection always uses the first ordered candidate or candidate group.

### Exact provider targets

`fixer-core` will define a validated `ProviderTarget` containing:

- media kind
- provider ID
- external ID

The target is generic even though the first Web UI exposes TMDB. TMDB IDs must be positive decimal strings, and media kind must be movie or television.

### Auditable execution reports

The output executor will return a complete bounded execution report rather than counts alone. Each operation records its kind, source path when applicable, destination path, outcome, and post-write fingerprint. This report is safe to persist and is the authority used by correction overwrite checks.

Correction replacement is allowed only when the destination path appears in the previous successful report and its current fingerprint equals the previous post-write fingerprint. Unknown or changed files fail closed.

## SDK Changes

`fixer-sdk` will expose a first-class scrape workflow instead of requiring callers to compose search, selected-candidate resolution, planning, and execution themselves.

Conceptually:

```rust
fixer
    .scrape(scanned_media)
    .selection(ScrapeSelection::Automatic)
    .resolve()
    .await?;

fixer
    .scrape(scanned_media)
    .selection(ScrapeSelection::Exact(provider_target))
    .resolve()
    .await?;
```

The SDK owns these rules:

- `Automatic` searches providers in configured order, preserves provider-native order, selects the first identity group, fetches it, and merges it with local metadata.
- `Exact` skips search, selects the named provider, issues `FetchRequest` for the exact external ID, and merges the fetched document with local metadata.
- Missing providers, unsupported media kinds, empty search results, and provider failures return typed errors.
- Search for correction returns ordered candidate identities without confidence values.
- The resolved scrape value includes the selected provider target, resolved media, warnings, and data needed by output planning.

The SDK output layer continues to use `fixer-core` plans and writers, but returns the new auditable execution report. The server supplies filesystem policy, destination, placement, template, and optional correction replacement manifest.

This keeps provider selection, exact-ID fetching, merge behavior, and scrape semantics reusable by the CLI and other SDK consumers.

## Queue and Runtime

Fixer will use Tokio's maintained bounded `mpsc` channel with messages containing only `ScrapeRunId`. No custom `VecDeque` queue and no external broker are introduced.

SQLite is the durable source of truth:

1. The API validates input and reserves channel capacity.
2. It inserts a `queued` run transactionally.
3. It sends the new ID through the reserved channel permit.
4. One worker receives IDs and loads all run input from SQLite.
5. The worker moves the run to `running`, executes the complete SDK workflow, and stores either an immutable result or a typed failure.

A single worker serializes filesystem mutation. This avoids destination races and makes correction fingerprint checks meaningful.

At startup, prior `running` rows become `queued`; all queued IDs are sent to the channel. A panic is contained per run and produces a failed record. If the channel is closed during submission, the server marks the new run failed and returns an unavailable response rather than silently accepting work that cannot run.

Iggy is intentionally deferred. It becomes appropriate only if workers move into separate processes or hosts. The local single-binary deployment does not justify broker operations, authentication, storage, or another failure domain.

## Persistence

The new primary table is `scrape_runs`:

```text
id
input_json
status
progress_json
result_json
error_json
previous_run_id
run_kind
created_at_ms
started_at_ms
completed_at_ms
```

`input_json` contains the source, destination policy, media kind when known, automatic or exact selection, organization settings, and configuration snapshot identity.

`result_json` contains:

- selected title, year, media kind, provider, and external ID
- the resolved media DTO used to render output
- non-fatal warnings
- destination and naming policy
- every attempted file operation
- successful output fingerprints

`error_json` contains a stable code, safe message, phase, and any bounded operation details.

`ingestion_sources.job_id` becomes `scrape_run_id`. Its user-visible statuses become pending, processing, succeeded, failed, or paused; there is no needs-review state.

A migration copies old jobs into historical scrape runs using the same numeric IDs when possible. Terminal jobs map to succeeded or failed summaries. Nonterminal jobs become failed with `legacy_interrupted`. Because old rows do not contain full resolved metadata or operation bytes, imported rows include a `legacy_incomplete` marker. Old tables are removed only after successful copy and foreign-key migration.

## Public API

```text
POST /api/v1/scrapes
GET  /api/v1/scrapes
GET  /api/v1/scrapes/{id}
GET  /api/v1/scrapes/{id}/events
GET  /api/v1/scrapes/{id}/correction-options
POST /api/v1/scrapes/{id}/corrections
POST /api/v1/scrapes/{id}/retry
```

A create request supports automatic selection:

```json
{
  "source": { "root_id": 1, "path": "Movies/Arrival" },
  "selection": { "mode": "automatic" }
}
```

Or an exact provider target:

```json
{
  "source": { "root_id": 1, "path": "Movies/Arrival" },
  "media_kind": "movie",
  "selection": {
    "mode": "provider_id",
    "provider": "tmdb",
    "external_id": "329865"
  }
}
```

Creation itself authorizes output writes. Browser writes retain authentication, CSRF protection, root-bound path validation, and an `Idempotency-Key`.

Correction options are fresh provider search results represented by title, year, media kind, provider, and external ID. They do not contain confidence. Submitting one exact candidate creates a correction run; the server never trusts display metadata from the browser.

The old job, review, plan, execute, cancel, and retry routes are removed. Old Web routes redirect to `/scrapes` without preserving Job terminology.

## Web Experience

Primary navigation becomes `刮削 / 刮削记录 / 设置`.

The scrape page contains a source directory picker and one primary action. A matched folder rule supplies destination, placement, and media kind. When no rule matches, the page asks for the missing organization settings once and can save them as a rule.

An optional `指定作品` disclosure accepts media kind and TMDB ID. It changes the primary action to `按 TMDB ID 刮削`.

After submission, the page says `刮削已开始，可以离开此页面` and shows the new run in recent activity. It does not force navigation to a progress page.

The records page lists source, selected work when known, start time, and the four public states in Chinese. A running row may show a plain-language transient phase such as `正在获取 TMDB 元数据`; it never shows internal state names, confidence, or percentages.

The audit page shows:

- selected work and artwork
- provider and external ID
- persisted resolved metadata
- before/after file paths
- written metadata files and fingerprints
- warnings or failure details
- retry and correction actions
- linked history with the latest successful result emphasized

Correction supports provider search and direct TMDB ID input. Submitting either starts a background correction immediately.

## Error Handling

No candidate, exact-ID not found, provider failure, output collision, changed correction target, and partial filesystem failure all produce terminal failed runs.

A retry clones the failed run's input into a linked retry. A correction uses a new exact target and replacement manifest. Partial execution is never summarized as success; all successful and failed operations remain in the audit result or failure details.

The no-overwrite rule remains for unrelated files. Correction is the only overwrite path and is constrained by the previous execution report and fingerprints.

## Configuration and Compatibility

`auto_accept_confidence` and `review_confidence` are removed from runtime configuration, Web settings, example configuration, validation, documentation, and tests. Existing config files containing these fields receive a targeted migration or deprecation error with an actionable message; they are not silently interpreted.

Provider order remains configuration-driven and becomes the primary cross-provider precedence. Provider-native search order is preserved inside each provider.

The CLI will adopt SDK automatic and exact-target behavior, but its command syntax remains separately documented. Existing preview-only CLI behavior can remain unless explicitly changed; this design changes the shared selection semantics, not every CLI write-safety default.

## Verification

Core tests cover categorical deterministic ordering, exact identity grouping, absence of confidence/tie behavior, execution reports, and replacement fingerprint guards.

SDK tests cover automatic first selection, exact provider fetch without search, provider/media validation, correction search ordering, and resolved scrape output.

Server tests cover queue backpressure, one-worker serialization, startup recovery, immutable results, retry/correction links, migration, ingestion integration, authentication, CSRF, idempotency, and SSE reconnection.

Web tests cover one-click submission, optional TMDB ID, records, persisted audit rendering, correction search, direct-ID correction, failures, responsive layouts, and the absence of Job, review, plan, and confidence terminology.

The end-to-end test starts a scrape, leaves the page, waits for completion from the records page, audits written files, corrects it with another TMDB ID, and verifies that the original audit record remains available.
